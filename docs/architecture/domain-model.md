# Financial domain model (proposed)

> Phase 1 design artifact — **proposal, not implemented**. Open decisions and
> their approval status are tracked in
> [`docs/decisions/decision-register.md`](../decisions/decision-register.md).
> Rules for money and accounting live in
> [`accounting-rules.md`](./accounting-rules.md) and ADR-0003/ADR-0004.

This document defines the proposed Prisma/PostgreSQL model for the MVP so a
later implementation task can create one reviewed migration without
guessing. It follows `requirements.md` §9.1 and §9.2.

## Conventions

- **IDs:** string UUIDs (`@default(uuid())`, `@db.Uuid` where practical) for
  user-visible resources; `cuid`/`uuid` must be chosen once — this document
  proposes `uuid`.
- **Timestamps:** `createdAt`/`updatedAt` on every app-owned table;
  occurrence timestamps are `timestamptz` (UTC). Period math uses the user's
  IANA timezone (see accounting rules).
- **Money:** integer minor units in `BIGINT` plus an ISO 4217 `currency`
  string. MVP accepts `BDT` only, enforced server-side through the currency
  registry (ADR-0003). No floats, no `NUMERIC` money columns.
- **Ownership:** every user-owned table has `userId` and every query is scoped
  to the verified session identity. Better Auth's tables are generated by its
  CLI and extended only where needed.
- **Derived values are never stored** (balances, goal progress, budget
  utilization, report totals) — see ADR-0004.

## Entities

### Better Auth-owned (generated, renamed where colliding)

| Model          | Purpose                              | Notes                                                                        |
| -------------- | ------------------------------------ | ---------------------------------------------------------------------------- |
| `User`         | Identity, email, display name        | Extended via Better Auth `additionalFields` only when necessary              |
| `Session`      | Server-side sessions (revocation)    | Owned by auth layer; app code never writes rows directly                     |
| `AuthAccount`  | Credential/OAuth identities per user | **Renamed via `modelName`** — otherwise it collides with financial `Account` |
| `Verification` | Email verification / recovery tokens | Used from Phase D once the email provider is wired                           |

The app never duplicates password hashes or provider secrets outside these
tables (§9.1).

### `Account` (financial account/wallet)

| Field                   | Type               | Rules                                                   |
| ----------------------- | ------------------ | ------------------------------------------------------- |
| `id`                    | uuid               | PK                                                      |
| `userId`                | string             | FK → `User.id`, indexed, `onDelete: Cascade`            |
| `name`                  | string(1–80)       | Trimmed, required, unique per user (case-insensitive)   |
| `type`                  | `AccountType` enum | `CASH`, `BANK`, `MOBILE_WALLET`, `SAVINGS`, `OTHER`     |
| `currency`              | string(3)          | ISO 4217; MVP registry = `BDT` only                     |
| `openingBalanceMinor`   | bigint             | May be zero or positive or negative; set at creation    |
| `status`                | `AccountStatus`    | `ACTIVE`, `ARCHIVED`                                    |
| `archivedAt`            | timestamptz?       | Set when archived; archive never deletes history (§5.3) |
| `createdAt`/`updatedAt` | timestamptz        |                                                         |

Rules: opening balance becomes immutable once the account has transactions —
later corrections are `ADJUSTMENT` transactions (ADR-0004). No stored balance
column.

### `Category`

| Field                   | Type             | Rules                                                   |
| ----------------------- | ---------------- | ------------------------------------------------------- |
| `id`                    | uuid             | PK                                                      |
| `userId`                | string           | FK → `User.id`, indexed, cascade                        |
| `name`                  | string(1–60)     | Display name                                            |
| `nameKey`               | string           | Lowercased/trimmed name for case-insensitive uniqueness |
| `type`                  | `CategoryType`   | `INCOME` or `EXPENSE`                                   |
| `color`                 | string?          | Optional UI hint; meaning is never color-only (§5.5)    |
| `status`                | `CategoryStatus` | `ACTIVE`, `ARCHIVED`                                    |
| `createdAt`/`updatedAt` | timestamptz      |                                                         |

Constraints: `@@unique([userId, nameKey, type])`. Default categories are
**cloned per user at first sign-in** from a seed definition — every
category has an owner, avoiding nullable-owner query branches.
**Implemented (IT-5, owner ruling 2026-10-17):** the seed is Salary,
Freelance, Gifts (income) and Groceries, Transport, Food & dining,
Utilities, Other expense (expense), each with a hex colour. Cloning runs
in the sign-up hook (`databaseHooks.user.create.after`) and again
idempotently on the first categories read, which backfills users created
before IT-5; `apps/api/src/modules/categories/category-defaults.ts` is the
one place the list lives.
Deletion: only when unreferenced by any transaction; otherwise archive
(§5.5). Archived categories keep historical reports readable. Renames
recompute `nameKey` and are allowed while archived; `type` is immutable.

### `Transaction`

| Field                   | Type              | Rules                                                             |
| ----------------------- | ----------------- | ----------------------------------------------------------------- |
| `id`                    | uuid              | PK                                                                |
| `userId`                | string            | FK → `User.id`, indexed                                           |
| `type`                  | `TransactionType` | `INCOME`, `EXPENSE`, `TRANSFER`, `ADJUSTMENT` (MVP)               |
| `amountMinor`           | bigint            | Strictly > 0 (§5.4); direction comes from `type`                  |
| `currency`              | string(3)         | Must equal the involved account(s) currencies                     |
| `occurredAt`            | timestamptz       | UTC; must not be in the future (MVP rule, ADR-0004)               |
| `accountId`             | uuid?             | Required for `INCOME`, `EXPENSE`, `ADJUSTMENT`                    |
| `fromAccountId`         | uuid?             | Required for `TRANSFER`; ≠ `toAccountId`                          |
| `toAccountId`           | uuid?             | Required for `TRANSFER`                                           |
| `categoryId`            | uuid?             | Required for `INCOME`/`EXPENSE`; null for `TRANSFER`/`ADJUSTMENT` |
| `adjustmentSign`        | smallint?         | `+1`/`−1` for `ADJUSTMENT` only                                   |
| `note`                  | string(0–500)?    | Optional description; **required** for `ADJUSTMENT`               |
| `idempotencyKey`        | string?           | Unique per user; replays return the stored record                 |
| `createdAt`/`updatedAt` | timestamptz       |                                                                   |

Constraints and indexes:

- `@@unique([userId, idempotencyKey])`.
- Check constraints added as raw SQL in the migration (Prisma cannot express
  them): type-specific required columns (e.g. `TRANSFER` requires
  `fromAccountId`/`toAccountId` and null category; `INCOME`/`EXPENSE` require
  `accountId`/`categoryId`), `amountMinor > 0`, `adjustmentSign ∈ {−1, 1}`,
  `fromAccountId <> toAccountId`.
- Indexes for real query patterns: `(userId, occurredAt DESC)`,
  `(userId, accountId, occurredAt DESC)`, `(userId, categoryId, occurredAt)`,
  `(userId, type, occurredAt)`. Avoid speculative indexes (§9.2).

Notes:

- `REFUND`, `tags`, and recurring references are **deferred**; the schema keeps
  room for a later additive migration (ADR-0004).
- Transfers are one row (both account references), not double-entry pairs
  (requirements.md §9.1).
- Transactions are hard-deleted with an audit event (ADR-0004).

### `Goal` and `GoalContribution`

| `Goal` field            | Type           | Rules                                                                                 |
| ----------------------- | -------------- | ------------------------------------------------------------------------------------- |
| `id`                    | uuid           | PK                                                                                    |
| `userId`                | string         | FK → `User.id`, indexed                                                               |
| `name`                  | string(1–80)   |                                                                                       |
| `type`                  | `GoalType`     | `GENERAL`, `EMERGENCY_FUND`, `EDUCATION`, `DEVICE`, `TRAVEL`, `DEBT_PAYOFF`, `CUSTOM` |
| `targetMinor`           | bigint         | Strictly > 0                                                                          |
| `currency`              | string(3)      | BDT in MVP                                                                            |
| `startDate`             | date           |                                                                                       |
| `deadline`              | date?          | Optional; if set, must be ≥ startDate                                                 |
| `priority`              | `GoalPriority` | `LOW`, `MEDIUM`, `HIGH` (display ordering)                                            |
| `status`                | `GoalStatus`   | `ACTIVE`, `PAUSED`, `COMPLETED`, `ARCHIVED`                                           |
| `createdAt`/`updatedAt` | timestamptz    |                                                                                       |

| `GoalContribution` field | Type        | Rules                                          |
| ------------------------ | ----------- | ---------------------------------------------- |
| `id`                     | uuid        | PK                                             |
| `userId`                 | string      | FK → `User.id`                                 |
| `goalId`                 | uuid        | FK → `Goal.id`, indexed, cascade               |
| `amountMinor`            | bigint      | Positive = contribution, negative = reversal   |
| `occurredAt`             | timestamptz |                                                |
| `note`                   | string?     |                                                |
| `reversesContributionId` | uuid?       | Unique; links a reversal to the original row   |
| `createdAt`              | timestamptz | Contributions are immutable (reversal pattern) |

Progress is always `Σ amountMinor`; no stored amount on `Goal`
(ADR-0005). A contribution created with only a local date is anchored at
00:00 local time in `Asia/Dhaka`; a reversal is recorded at the instant it is
created. Neither row is a transaction: accounts, income/expense totals, and
budgets never see them.

### `Budget` and `BudgetCategoryLimit`

| `Budget` field          | Type           | Rules                                          |
| ----------------------- | -------------- | ---------------------------------------------- |
| `id`                    | uuid           | PK                                             |
| `userId`                | string         | FK → `User.id`, indexed                        |
| `name`                  | string(1–80)   |                                                |
| `period`                | `BudgetPeriod` | `MONTHLY` in MVP (weekly/yearly in V1)         |
| `startDate`             | date           | First day of the budget period (user timezone) |
| `totalLimitMinor`       | bigint?        | Optional total budget                          |
| `status`                | `BudgetStatus` | `ACTIVE`, `PAUSED`, `ARCHIVED`                 |
| `createdAt`/`updatedAt` | timestamptz    |                                                |

| `BudgetCategoryLimit` field | Type   | Rules                                           |
| --------------------------- | ------ | ----------------------------------------------- |
| `id`                        | uuid   | PK                                              |
| `budgetId`                  | uuid   | FK → `Budget.id`, cascade                       |
| `categoryId`                | uuid   | FK → `Category.id`; must be an EXPENSE category |
| `limitMinor`                | bigint | Strictly > 0                                    |

Constraints: `@@unique([budgetId, categoryId])`, `1 ≤ limits ≤ 50` per
budget (validated in service). Overlapping active budgets for the same
category are prevented in the service layer (documented rule: one active
budget limit per category per period); a DB-level exclusion constraint is
possible but judged overkill for MVP — record as an implementation note.

### `UserPreference`

| Field                   | Type        | Rules                                                  |
| ----------------------- | ----------- | ------------------------------------------------------ |
| `id`                    | uuid        | PK                                                     |
| `userId`                | string      | FK → `User.id`, unique (1:1), cascade delete           |
| `locale`                | enum        | `EN` or `BN`; default `EN`                             |
| `timezone`              | varchar(64) | IANA name, validated server-side; default `Asia/Dhaka` |
| `currency`              | varchar(3)  | `BDT` in MVP (ADR-0003); default `BDT`                 |
| `theme`                 | enum        | `LIGHT`, `DARK`, `SYSTEM`; default `LIGHT`             |
| `weekStartsOn`          | enum        | `SUNDAY`…`SATURDAY`; default `SATURDAY` (DR-11)        |
| `dateFormat`            | enum        | `DMY`, `MDY`, `YMD`; default `DMY`                     |
| `numberFormat`          | enum        | `LOCALE`, `LATIN`, `BENGALI`; default `LOCALE`         |
| `reducedMotion`         | enum        | `SYSTEM`, `REDUCE`; default `SYSTEM`                   |
| `createdAt`/`updatedAt` | timestamptz |                                                        |

A missing row is valid and yields documented defaults. Preferences are
display/reporting settings only; they never alter recorded financial data.
Notification preferences are added with V1 notifications.

### `DashboardLayout`

| Field                   | Type        | Rules                                                           |
| ----------------------- | ----------- | --------------------------------------------------------------- |
| `id`                    | uuid        | PK                                                              |
| `userId`                | string      | FK → `User.id`, unique in MVP (single layout), cascade          |
| `layout`                | jsonb       | `{ version: 1, widgets: [{ id, visible }] }`, service-validated |
| `createdAt`/`updatedAt` | timestamptz |                                                                 |

Stored layout is **validated structured data** (ordered supported widget IDs
and visibility), never executable JSON/CSS (§5.7). Writes must name every
supported widget exactly once; unknown/duplicate/stale entries are dropped
safely on read and missing widgets are appended. A "reset to default" deletes
the saved row and restores the documented default layout. Multiple named
layouts remain DR-12 (V1).

### `AuditEvent`

| Field          | Type             | Rules                                                                             |
| -------------- | ---------------- | --------------------------------------------------------------------------------- |
| `id`           | uuid             | PK                                                                                |
| `userId`       | string?          | Nullable after account deletion; no cascade into events                           |
| `type`         | `AuditEventType` | e.g. `TRANSACTION_DELETED`, `ACCOUNT_DELETED`, `DATA_EXPORTED`, `SESSION_REVOKED` |
| `resourceType` | string?          | e.g. `transaction`, `account`                                                     |
| `resourceId`   | string?          |                                                                                   |
| `metadata`     | jsonb?           | Safe, minimal metadata only — no amounts, notes, tokens                           |
| `createdAt`    | timestamptz      |                                                                                   |

MVP records audit events for destructive/security-relevant actions only
(§9.1, DR-16); no full request bodies and no secrets.

## Relationships (textual ERD)

```text
User 1─* Session                      (auth, library-owned)
User 1─* AuthAccount                  (auth, library-owned; renamed)
User 1─* Account                      (financial)
User 1─* Category
User 1─* Transaction
User 1─* Goal 1─* GoalContribution
User 1─* Budget 1─* BudgetCategoryLimit *─1 Category
User 1─1 UserPreference
User 1─1 DashboardLayout              (MVP)
User 1─* AuditEvent                   (userId nullable for anonymized history)

Transaction *─1 Account               (accountId; INCOME/EXPENSE/ADJUSTMENT)
Transaction *─1 Account               (fromAccountId; TRANSFER)
Transaction *─1 Account               (toAccountId; TRANSFER)
Transaction *─1 Category              (INCOME/EXPENSE)
```

## Delete / archive behavior (must be enforced server-side)

| Resource     | Default action             | Hard delete allowed?                                        |
| ------------ | -------------------------- | ----------------------------------------------------------- |
| Account      | Archive                    | Only via full account deletion; history never silently lost |
| Category     | Archive when referenced    | Delete only when unreferenced (else 409 with message)       |
| Transaction  | Hard delete + confirmation | Yes, with audit event                                       |
| Goal         | Archive/complete           | Delete allowed; contributions cascade after confirmation    |
| Contribution | Reverse (linked row)       | Never deleted — reversal preserves history                  |
| Budget       | Archive                    | Delete allowed with confirmation                            |
| User         | Account deletion workflow  | Cascades all owned data (retention policy per DR-16)        |

## Deliberately not in the MVP schema

- `RecurringRule`, notifications, AI conversations (V1 — they get their own
  migrations).
- Multi-currency conversion, exchange-rate tables (§3.3 later).
- Account-linked goal allocations (ADR-0005 documents the additive path).
- Tags and custom fields (V1).
- Stored/cached balances or report aggregates (§9.2).
