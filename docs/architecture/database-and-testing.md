# Database and testing strategy

> Implemented by IT-2 (2026-10-16) under the accepted ADR-0007 — this
> document describes the actual setup. Register entry:
> [`docs/decisions/decision-register.md`](../decisions/decision-register.md)
> (DR-05). Requirements: `requirements.md` §9.2, §11.2, §12, §14, §15.

## Environments

| Environment | Database                                                          | Purpose                             |
| ----------- | ----------------------------------------------------------------- | ----------------------------------- |
| Local dev   | Docker PostgreSQL 16 (`infrastructure/docker/docker-compose.yml`) | Development against disposable data |
| Local test  | Same Docker instance, `moneyflow_test` database                   | Integration tests                   |
| CI          | GitHub Actions `postgres:16` service container                    | Integration tests on PRs            |
| Staging     | Neon branch (or separate project)                                 | Pre-production verification         |
| Production  | Neon project (AWS Asia Pacific / Singapore)                       | Real user data                      |

No production user data is ever copied into development or test
environments (§9.2, §12.4).

## Prisma 7 + Neon connection design (ADR-0007)

- **Runtime:** `@prisma/adapter-pg` (node-postgres) with the **pooled**
  `DATABASE_URL` (Neon `-pooler` host, PgBouncer transaction pooling).
- **Prisma CLI (migrations/introspection):** **unpooled** `DIRECT_URL` via
  `prisma.config.ts` (`process.env.DIRECT_URL || env('DATABASE_URL')`).
  Locally it falls back to `DATABASE_URL`, which points at the Docker
  database.
- **SSL:** `sslmode=require` on every remote URL; `disable` only for
  `localhost`.
- **Cold starts:** Neon computes scale to zero; set `connect_timeout=15` and
  explicit pool settings (`connectionTimeoutMillis`, modest `max`) in the
  adapter so the first request does not fail fast. Prisma 7 `pg` defaults
  changed from v6 (no connect timeout, 10s idle) — set them deliberately.
- **Generated client:** Prisma 7 writes to an explicit output path
  (`apps/api/src/generated/prisma`); it is git-ignored and regenerated by
  `prisma generate` through package pre-scripts (dev/build/typecheck/test)
  and explicit CI setup. Imports use that path, not `@prisma/client`.
- **Client lifecycle:** one client per process, owned by a `PrismaService`
  with `onModuleInit`/`onModuleDestroy` (`$disconnect`) — no per-request
  client creation.

Alternatives considered: `@prisma/adapter-neon` (official Neon path for
serverless/edge — unnecessary for a long-running NestJS server; can be
adopted if the API is ever deployed to an edge/serverless runtime),
Supabase/Railway/Render Postgres (no branching or platform value needed
here), self-managed PostgreSQL (ops burden).

## Migration workflow

1. **Author (local):** `prisma migrate dev --name <change>` against Docker;
   generated SQL is reviewed (destructive statements, lock risk) before
   commit; hand-edited SQL is allowed for CHECK constraints and partial
   indexes (`requirements.md` §9.2, ADR-0004 transaction checks).
2. **Commit:** migrations live in `apps/api/prisma/migrations/` and are never
   edited after being applied to shared environments.
3. **CI:** fresh database + `prisma migrate deploy`, then integration tests.
4. **Deploy:** `prisma migrate deploy` runs against the direct URL before the
   new API version starts; failed migrations stop the rollout (§15.3).
5. **Forbidden:** `db push` against shared environments; manual schema edits;
   `migrate reset` on anything that is not a throwaway local database.

Later schema changes follow expand → migrate → contract for anything risky.
The initial migration landed with IT-2 (2026-10-16): generated with
`prisma migrate diff`, then hand-extended with the CHECK constraints and
the functional unique index as one reviewed migration. Later additive
migrations: IT-9 `20261019173444_add_budgets` (`budget`,
`budgetCategoryLimit`, month-anchor and positive-limit CHECKs); IT-10
`20261020163000_add_goals`; IT-11 `20261020190000_add_preferences_and_layout`;
IT-12 `20261020203000_add_audit_events` (audit enum/table, metadata-object
CHECK, and user/type indexes). IT-12 changes no financial table.

## Local development setup (implemented by IT-2)

- `docker compose up` starts PostgreSQL 16 as today; the compose file
  mounts `infrastructure/docker/initdb/`, which creates the
  `moneyflow_test` database on first startup (fresh volumes; see the
  runbook for existing volumes).
- `.env` (git-ignored) and `.env.example` carry `DIRECT_URL` and
  `TEST_DATABASE_URL` placeholders.
- All timestamps are stored as `timestamptz(3)` (`@db.Timestamptz(3)`),
  including the Better Auth tables, so every stored instant is an
  unambiguous UTC point. **Session pinning (2026-10-19):** the Prisma
  driver adapter serializes `DateTime` values as timezone-naive text that
  PostgreSQL interprets in the _session_ timezone, so on a server whose
  default is not UTC every stored instant was silently shifted by the
  session offset (found while running the IT-8 integration suite on a
  UTC+6 machine; UTC-based CI never exposed it). `buildPrismaClientOptions`
  now pins every pooled connection with `options: '-c TimeZone=UTC'`, and
  the integration suite (`schema.test.ts`) asserts both the session
  timezone and a server-rendered stored instant so any regression is
  visible on any host.

## Testing strategy

### Unit tests (no database)

- Money: minor-unit parsing/formatting, currency exponent, strict scale
  validation, max guard, contract serialization (`BigInt` → string).
- Balance and summary rules: the full effect matrix, the worked example in
  [`accounting-rules.md`](./accounting-rules.md) §8, edit/delete
  re-derivation, refund-aware aggregation, percentage rounding.
- Period math: `Asia/Dhaka` day/week/month boundaries, week-start preference,
  month-end, DST fixtures for a second timezone.
- Customization schema validation, contract DTO validation.
- CSV encoding (BOM/CRLF/RFC 4180 quoting/formula neutralization), export
  filter parsing, filename generation, deletion input validation, and the
  in-memory rate limiter.
- These run in the current database-free CI job and must stay fast.

### Integration tests (real PostgreSQL)

- Run against `TEST_DATABASE_URL` only. A safety guard refuses to run if the
  URL host is not `localhost`/`127.0.0.1` or the CI service host.
- Setup: `prisma migrate deploy` on an empty test database; truncate between
  suites; deterministic synthetic fixtures only (§12.4).
- Cover: transaction create/edit/delete consistency, transfer atomicity,
  goal contribution/reversal, budget utilization (month boundaries,
  expense-only counting, status moves, overlap rule), idempotent replays,
  uniqueness constraints, CHECK constraints, pagination/filtering, CSV
  export filters/format/streaming and audit atomicity, full account deletion
  with rollback and session invalidation, and **cross-user isolation** for
  every resource, nested resource, and export.
- Concurrency smoke test: two simultaneous creates do not corrupt aggregates.

### End-to-end tests (later phase)

- The MVP critical flows in §12.3 (sign-up, first account, income/expense,
  transfer not counted as income/expense, goal contribution, budget usage,
  dashboard persistence, export, cross-user denial, deletion).
- Framework decision (e.g. Playwright) is deferred to the phase that adds it;
  it is a new dependency and gets its own recorded choice.

### Test data rules

- Deterministic fixtures; no real personal records; boundary values (0, 1
  minor unit, max, over-max, extra decimals), timezone/month/year edges,
  duplicate/retry scenarios, archived categories/accounts with history.

## Operational notes (owner decisions pending)

- **Backups / RPO / RTO:** depends on the Neon plan (free tier has limited
  history; paid plans offer point-in-time restore). Tracked as register
  DR-15; a restore runbook must be written and actually tested before public
  launch (§10.1, §11.2).
- **Least privilege:** separate database roles/projects per environment;
  credentials rotated on exposure; never reused between dev and production.
- **Observability:** request IDs, safe error categories, no financial content
  or secrets in logs (§15.4).
- **Health checks:** `/api/v1/health` reports `status: ok|degraded` plus a
  `database: up|down|not_configured` readiness field since IT-2; a failing
  database degrades the payload instead of crashing the process.
